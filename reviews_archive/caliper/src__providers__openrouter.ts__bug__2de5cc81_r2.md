## Verdict
Not clean. The same-sha delta since the last bug review is nil (sha unchanged from 2de5cc81's review target), but hunting beyond that record surfaces four unrecorded defects, two on the real-money path: a mid-stream rejection that discards the accumulated partial answer — directly contradicting this file's own half-answer doctrine and reachable by the file's own 120s timeout on an explicitly minutes-long stream — and a 200-but-not-SSE body silently swallowed into an empty success.

## Bugs & vulnerabilities

- **[HIGH] Mid-stream rejection discards the partial answer the file promises to keep - `line 124` (with `line 100`, `line 173`)** — What: `consumeChatStream` awaits `readSseLines` with no try/catch; `readSseLines`' `await reader.read()` (line 101) is likewise unguarded. If the read rejects, the promise chain throws and `content`/`usage`/`toolAcc` accumulated so far are discarded — despite the function's own comment (lines 116-118: "A stream that ends without [DONE] still yields what arrived - a half answer with its truth beats a hang"). That doctrine covers clean EOF only, not the error path. Trigger: (a) network drop/reset mid-body, or (b) guaranteed: `AbortSignal.timeout(120_000)` (line 173) fires 120s after request start and, per fetch semantics, aborts in-flight body reads — while line 113-114 explicitly designs for "a brain that thinks for minutes", so any stream longer than 2 minutes is killed mid-read by design. Impact traced end-to-end: deltas already reached the user via `onDelta` (the live-progress rule), then `vite.agent.ts` `callBrain` (~line 296) rethrows everything non-429 — the console shows a ticking answer that suddenly errors with nothing, and `usage` is lost so the question's cost truth is never reported after real spend. Fix: wrap the line-124 await in try/catch (or catch around the read loop) and return the accumulated state on rejection; for the streaming twin, apply the timeout to connection establishment only or raise it, since minutes-long streams are the advertised case. CONFIRMED (code path certain; abort-fires-mid-read is standard fetch behavior; independently re-verified against current bytes by the hunt orchestrator).

- **[MEDIUM] A 200 response that is not an SSE body is silently converted into an empty successful reply - `line 181` (with `line 95`)** — What: `openRouterChatStream` checks `res.ok` then hands `res.body` to `consumeChatStream` without checking `content-type`. `readSseLines` delivers only lines starting with `data:` (line 95), so a plain JSON body yields zero lines → `{ content: "", toolCalls: [], usage: null }` returned as success. Trigger: a provider/route that ignores `stream: true` and answers non-streamed (OpenRouter routes through upstream fallbacks; also any 200 HTML/JSON error page from an intermediary). Impact: the agent loop receives an empty model turn — no error, no content, no tool calls — the exact "silent failure" class; the non-stream parser (`parseChatCompletion`) exists one function up but is never used as fallback. Fix: on ok, branch on `res.headers.get("content-type")` — JSON → `parseChatCompletion(await res.json())`, else stream. PLAUSIBLE (unverified because no live non-SSE 200 repro is in the record; the swallow path itself is certain from code).

- **[MEDIUM] Unguarded `res.json()` on ok responses throws raw SyntaxError past the file's own `.catch(() => null)` discipline - `line 190` (fetchPricing), `line 81` (openRouterChat)** — What: both fetches guard network failure with `.catch(() => null)` and guard `!res.ok`, but a 200 with a non-JSON body makes `await res.json()` throw an unwrapped `SyntaxError`. In `fetchPricing` this also skips `pricingCache.set` (line 194), so the failure is not even cached — every subsequent question re-hits the broken parse. Trigger: 200 + HTML/garbage from gateway or captive intermediary. Impact: consumer `vite.agent.ts:342` calls `await fetchPricing(...)` inline in `respondWith` with no visible try — the question can error *after* the answer was computed and money spent; for `openRouterChat` the caller gets an undecorated parse error instead of the file's `openrouter ...` error shape. Fix: `.catch(() => null)` the json parse in both, mirroring the fetch guards. PLAUSIBLE for the vite.agent.ts blast radius (surrounding try not re-read); the parse-crash itself CONFIRMED by reading.

## Missing safeguards
- No `content-type` verification before consuming a streamed body (finding 2) — one header check would close the silent-empty class.
- No try/catch anywhere in the read loop or around `readSseLines`; the reader is also never `cancel()`ed/`releaseLock()`ed on the exception path, abandoning the body lock.
- No `Number.isFinite`/non-negative validation on external numeric input (catalog prices, streamed usage fields) before it becomes displayed cost.
- Auth-header asymmetry: `openRouterChat` sends `authorization: Bearer ${token}` unconditionally (line 65) while the stream twin guards empty tokens (line 163) — safe only while the non-stream twin stays cloud-only and every llama.cpp sidecar runs without `--api-key`.
- `pricingCache` writes are skipped when the json parse path throws (finding 3) — the cache only ever records fetch-failure nulls, not parse-failure ones, so a broken 200 re-parses on every question.

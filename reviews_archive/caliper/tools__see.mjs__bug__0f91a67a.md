### Review

## Verdict
NOT SHIP-BLOCKING but not trustworthy for its one job. The tool's core claim — "render visible: true" plus a saved screenshot proves the just-queued render — is false on the common path, because the app rehydrates the previous session's render window from persisted storage before the wait loop even starts. Failure modes (Edge down, app down, selector timeouts) do exit non-zero via top-level-await crash, but with raw stacks, and soft failures (queue click refused, bundle not found) exit 0 and still save a screenshot.

## Bugs & vulnerabilities
- **[HIGH] Stale persisted media satisfies the completion check — the tool screenshots and certifies the PREVIOUS render** - `lines 38-45, 55` — CONFIRMED. What: the loop waits for ANY `img, video` inside `.pane-render`; it never verifies the media belongs to the job just queued. Trigger (end-to-end traced): run 1 completes → ScreenStage.tsx:51-54 auto-opens the done job's outputs as a non-minimized AssetWindow (renders `<img>`/`<video>`, ScreenStage.tsx:889-890) → screenStore persists `windows` under `caliper.screen` (screenStore.ts:223 `partialize` includes `windows`) → the header's own "persistent" `.see-profile` (see.mjs:6) reloads that window on the very first paint of run 2 → the loop's first probe (~2s in) finds the old media, breaks, and `page.screenshot` saves the OLD render while the new job is still queued/running; console says `render visible: true`. ScreenStage deliberately keeps earlier windows ("earlier windows stay where they were", ScreenStage.tsx:50), so nothing clears the pane during the new run. Impact: after the first successful run in a profile, every subsequent verification run can silently verify a stale artifact — precisely the false-confidence failure the repo's screenshot-verify protocol (AGENTS.md:56) exists to prevent, plus one wasted GPU render per misleading run. Fix: before queueing, clear the persisted screen (`localStorage.removeItem("caliper.screen")` + reload, like the CLEAR_PARAMS dance in tools/see-ui-720p.mjs:19-25), or capture a pre-queue fingerprint (media src/window id) and require it to CHANGE, or — best, matching the sibling — wait for the job-status text `/done · seed \d+/` as tools/see-ui-720p.mjs:74 does instead of mere media presence.
- **[MEDIUM] Silent no-op bundle selection renders and screenshots the wrong bundle** - `lines 24-27` — CONFIRMED. What: `opt?.click()` optional chaining swallows the not-found case; the flyout stays open with the previously selected bundle and the script queues that one instead. Trigger: bundle renamed in bundles.json, typo'd argv name, or the fixed 500ms sleep (line 23) racing a slow flyout render — the finder `[...document.querySelectorAll("button")].find(...)` simply misses. Impact: a wrong-bundle GPU render plus a screenshot artifact that looks valid (media IS present) — an agent verifying a bundle-specific change gets false confirmation. Nothing logs which bundle is actually selected. Fix: throw (or at minimum log loudly) when `opt` is undefined, and verify the picker afterwards exactly as tools/ui-harness.mjs:142 does (`picker shows "${picker}" after selecting ${name}`).
- **[LOW] `queued: false` still saves a screenshot and exits 0** - `lines 29-34, 46, 55` — CONFIRMED. What: when the Queue render button is disabled (single-render guard / problems, DeckControls.tsx:118) or missing, the run logs `queued: false`, then either burns the full 180s or (via the HIGH bug) exits instantly on stale media, saves `see-shot.png`, and exits 0. Impact: no failure contract — a caller gating on exit code (the discipline the sibling harness states, ui-harness.mjs:10 "Exit code 1 on any FAIL") sees success. Currently no script parses it, so this is degraded signal, not a broken contract. Fix: after cleanup, `process.exit(1)` when `!queued || !done`.
- **[LOW] No error handling around connect/goto/waits; failures leak an orphan app tab into the shared Edge** - `lines 16-22, 57-58` — CONFIRMED. What: any throw between `browser.newPage()` and `page.close()` (verified against the installed puppeteer-core 25.8.0: `getWSEndpoint` in BrowserConnector.js does a single fetch with no retry, so Edge-down rejects immediately — no hang, exit 1 via unhandled top-level rejection, but the message is a raw `Failed to fetch browser webSocket URL` stack that never mentions the header's launch command; same for a goto refusal when the app is down). The opened page is never closed, and it keeps polling LLM status every 5s (ScreenStage.tsx:43) and holds a ComfyUI websocket — repeated failing runs accumulate tabs in the deliberately long-lived shared Edge. Fix: wrap the body in try/finally (close page, disconnect) and preflight `127.0.0.1:9223/json/version` with a clear "start Edge per header" message, as ui-harness.mjs:32-43 already does.

## Missing safeguards
- No preflight of Edge-9223 / app-4173 with an actionable error (the ui-harness.mjs:25-43 pattern exists in-repo to copy).
- Hard-coded 180s cap (90 × 2s) is too short for heavy bundles — the sibling waits 600s for LTX 720p/10s (see-ui-720p.mjs:69); long renders get reported `render visible: false` and screenshotted mid-run with no "timeout, still rendering" distinction.
- Screenshot silently overwrites `out` (default `see-shot.png` in CWD) — combined with the HIGH bug there is no way to tell a fresh artifact from a stale one; a timestamp or pre-save staleness check would help.
- No `APP_URL` override (ui-harness.mjs:16 has one), so the tool cannot point at `vite preview` vs `dev` variations without an edit.

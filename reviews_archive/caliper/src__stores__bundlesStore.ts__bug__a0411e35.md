## Bugs & vulnerabilities
**[MEDIUM] Silent, permanent, list-wide discard of the constraint-vocabulary migration when a file's own size_presets sit off the adopted factory grid** - `src/stores/bundlesStore.ts:124-133`
- What: load() merges factory constraints via `withFactoryConstraints`, then re-validates; on `rechecked.ok === false` it silently keeps the pre-merge `checked` — no PUT, no `fileIssues` entry, no message of any kind. The recheck CAN legitimately fail: the schema's adoption gates cover the file's *defaults* but not its *declared* presets. `schema.ts:105-111` adopts `width_multiple`/`height_multiple` whenever the file's defaults are on the factory grid, and `schema.ts:216-224` then validates the file's own (unadopted, hand-declared) `size_presets` against the newly adopted multiples.
- Trigger (traced end-to-end): a factory-id bundle (e.g. LTX-2.3-Distilled) hand-edited to carry `size_presets: [{label:"ODD", width:1000, height:1000}]` with no `width_multiple`/`height_multiple` keys and on-grid defaults (768x512). Pre-merge validation passes (grid checks at schema.ts:223-224 are skipped while the multiple is undefined); the merge adopts 16-grids (defaults are on-grid); the recheck then rejects preset "ODD" (1000 % 16 = 8) → entire merge discarded for EVERY bundle in the file (recheck is all-or-nothing over the list), including the ids-adjacent lora_strength adoption.
- Impact: that file silently never gains any constraint (no VAE-grid snapping, no frames_max, no steps bounds — `widthMultiple` falls back to 1, so off-grid widths render cropped/padded, the exact harm the vocabulary exists to prevent), the discard repeats on every boot forever, and nothing tells the user why. Safe-direction (file untouched, no corruption) but a silent permanent functional vacuum.
- Fix: surface the discard (append a `ValidationIssue`-style note to `fileIssues` naming the bundle/field that blocked the migration), and/or in `withFactoryConstraints` skip adopting a multiple that would invalidate the file's already-declared presets (schema.ts:105-111), mirroring the existing "hand-edit always wins" gating used for presets themselves.
- CONFIRMED (pure dataflow trace; no runtime needed; re-verified against current bytes by the hunt orchestrator — the sibling frames_max axis of this same discard class was remediated this morning in bd2f0ec, the presets axis remains open).

**[MEDIUM] save()'s only error channel is its return value, and two shipped callers discard it — refusing presses become silent no-ops** - `src/stores/bundlesStore.ts:154-174` (with consumers `src/surfaces/BundlesSurface.tsx:79-81`, `src/surfaces/GenerateSurface.tsx:180`)
- What: save() reports every refusal exclusively through the returned `ValidationIssue[]` (not-yet-loaded guard `:156`, client validation `:160`, unreachable API `:169`, server refusal `:173`); it writes no store state on failure. `BundlesSurface.remove()` (`:79-81`) and GenerateSurface's AdvancedDrawer onChange (`:180`, `void ...save(...)`) drop that return value.
- Trigger (two concrete, reachable traces): (1) double-press remove on the LAST bundle → `save([])` → schema.ts:162-163 rejects the empty list → issues returned → dropped → the armed destructive press visibly "fires" and nothing happens, no message (also silent on any network refusal during remove). (2) In the Generate pane's advanced drawer, clearing the Name field (AdvancedDrawer.tsx:27-28) → schema.ts:169 "Name is required" → refusal dropped silently. Bonus defect in the same consumer line: it maps `x.name === b.name` with `b.name` already the NEW name, so a rename never matches and each keystroke PUTs an unchanged file while the input reverts.
- Impact: violates the repo's own "every button press must produce a visible result" rule; users see edits/removals silently not stick. (The other two callers — BundlesSurface's editor `:69-77` and addFromCatalog `:51-57` — handle the return correctly.)
- Fix: cheapest store-side hardening is to also write refusals into a surfaced field (e.g. `fileIssues` or a `lastSaveIssue`) so no caller can lose them; caller-side, `remove()` and the drawer onChange must consume the return like their siblings do (and the drawer should match by the bundle's old name/id).
- CONFIRMED statically at all four cited sites.

## Missing safeguards
- The two load() migration PUTs (`:117`, `:130`) are fire-and-forget with no ordering guarantee relative to each other or to a user save(); harmless today (idempotent, self-healing on next load, millisecond boot window on localhost) but a future faster-triggered save could interleave.
- save() has no in-flight guard: two overlapping saves (the drawer fires one per keystroke) apply their `set()` in response-arrival order, so a stale response can leave client state briefly diverged from the server file until the next load().
- Schema does not validate `defaults.frames` against the bundle's own detent (only params are detent-checked), so boot coercion (`:141`) can silently seat a frames value different from the file's stated default with no snap speech — intended for persisted edits, less so for file defaults.
- paramEdits/params/prompts/selection are name-keyed, so renaming a bundle in the editor orphans the user's tuned params and reselects the first bundle — documented trade-off (schema.ts:243), but re-keying by the immutable id would survive renames.
- `touched` recording (`:279`) keeps an edit that happens to equal the current file default, masking later default changes for that field — defensible (explicit user choice) but worth a conscious decision.

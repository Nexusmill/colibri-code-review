### Review

## Verdict
The cross-file contract is intact today, verified on both sides: bundle `LTX-2.3-Distilled` exists in bundles.json with `vae.video`/`vae.audio`/`text_encoders[0..1]`/`defaults{steps:8, cfg:1, frames:241, fps:24, 1280x720}`; the template's 13 `{{slots}}` (checkpoint, vae_video, vae_audio, text_encoder_1/2, prompt, seed, steps, cfg, width, height, frames, fps) are all supplied; SIGMAS is byte-identical to `LTX_DISTILLED_SIGMAS` in src/workflows/fill.ts:14; the slot-filling loop mirrors fillWorkflow (fill.ts:18-37); the bundle's `loras: []` keeps the no-lora claim true. Exit codes are correct on all three terminal paths. The real defects are robustness gaps the successor already fixed: an unbounded poll loop, an unreadable outputs line, and latent parity drift versus fill.ts's steps-gated sigma swap.

## Bugs & vulnerabilities
- **[MEDIUM] Unbounded wait loop — a dropped or wedged render spins "waiting"/"executing" forever** - `lines 54-70` — CONFIRMED. What: `for(;;)` polls /history every 15 s with no deadline; the sibling see-ui-720p.mjs:69 caps at 300×2 s = 600 s, and rebaseline.mjs was written as the hardened generalization. Trigger: (a) backend restarted mid-wait — the history entry for the prompt never appears, so `e` stays undefined and the loop logs "waiting" indefinitely; (b) a wedged render on the 16 GB shared card (a documented reality in this repo) loops on "executing" forever. Impact: the operator gets no nudge to intervene on a GPU that is burning hours; the render itself keeps running server-side regardless of script exit, but an unattended terminal never surfaces the stall. Fix: cap the loop (600-900 s like the siblings) and exit non-zero with the last status on timeout.
- **[LOW] DONE line prints "[object Object]" instead of output filenames** - `lines 64-66` — CONFIRMED. What: ComfyUI history outputs are `{nodeId: {images|gifs: [{filename, subfolder, type}]}}`; `Object.values(o).flat()` yields file-descriptor objects and `outs.join(", ")` stringifies them as `[object Object]`. Trigger: every successful run. Impact: the tool's stated deliverable ("reports duration + outputs") is half-broken — duration and exit code are right, but the evidence line is unusable for appending to knowledge/measured-results.md. Fix: map to `f.filename` (as the Library's `nameOf` does, ScreenStage.tsx:609) before joining.
- **[LOW] ManualSigmas swap is unconditional; fill.ts gates it on steps === 8 — a defaults change turns this into a lying measurement** - `lines 43-45` vs `src/workflows/fill.ts:94-100` — PLAUSIBLE (parity holds today at steps 8). What: this tool replaces every BasicScheduler with the 9-sigma ManualSigmas regardless of `p.steps`, and the swap discards the `{{steps}}` input (it lived on the replaced node), so the render is always the 8-step distilled schedule; fill.ts only swaps when `Math.floor(p.steps) === 8` and otherwise keeps the honest BasicScheduler. Trigger: someone changes the bundle default steps away from 8 in bundles.json. Impact: the tool then renders an 8-step schedule while its log (line 52) reports the new step count — a GPU-costing measurement that misattributes timing to a configuration that was never exercised. Fix: gate the swap on `p.steps === 8` to mirror fill.ts, or better, import `fillWorkflow`/`LTX_DISTILLED_SIGMAS` behavior parity explicitly.
- **[LOW] Hardcoded "loras: none" ignores `b.loras` — a bundle lora addition silently diverges the measurement from app behavior** - `line 52` (and the whole build, which never chains loras) vs `fill.ts:101-112` — PLAUSIBLE (bundle is lora-free today, verified). What/Trigger: add a LoRA to the LTX bundle in bundles.json; the app chains it via LoraLoaderModelOnly, this tool keeps rendering without it. Impact: re-baseline numbers appended to knowledge/measured-results.md would no longer describe what the app actually renders. Fix: either throw when `b.loras.length > 0` ("use rebaseline.mjs") or chain loras identically to fill.ts.
- **[LOW] Missing-bundle guard absent — a renamed id crashes with a bare TypeError** - `lines 13-14` — CONFIRMED. What: `file.bundles.find((x) => x.id === "LTX-2.3-Distilled")` with no null check before `b.defaults`; the successor rebaseline.mjs has exactly this guard (`if (!b) throw new Error(...)`). Trigger: bundle id rename or bundles.json restructure. Impact: an unhelpful `Cannot read properties of undefined (reading 'defaults')` instead of an actionable message. Fix: copy rebaseline's guard.

## Missing safeguards
- No residency normalization before queueing: rebaseline.mjs purges `/free` first and takes a warm render plus two timed renders precisely because "one model family at a time on 16 GB"; this tool queues onto whatever is resident, so its single duration number is cold/warm-dependent and not comparable across runs — fine for its original one-shot purpose, but worth a header caveat now that rebaseline exists.
- Unlike see-ui-720p.mjs:50-53, there is no refuse-to-queue sanity gate (the UI sibling verifies steppers show expected defaults before queueing); this tool reads the same bundles.json it measures, so it is self-consistent, but it cannot detect a stale-file vs running-app disagreement.
- Deletion note: only rebaseline.mjs's header comment cites this file (as pattern origin) — removing it breaks nothing functional; if kept, fix the MEDIUM loop bound first since a hung run leaves an unattended GPU render with no watchdog.

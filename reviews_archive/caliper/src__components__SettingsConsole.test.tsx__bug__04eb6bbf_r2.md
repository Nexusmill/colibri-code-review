## Bugs & vulnerabilities
- **[MEDIUM] Preset restore/delete assert the verb but never the promised outcome** - `line 403` / `line 409`. What: the test pins only `routePreset` call args. The component's restore chain (`SettingsConsole.tsx:237-240`: refetch routes/types/presets + status line) and the delete outcome (`SettingsConsole.tsx:251`: `setPresets(r.presets ?? Impact: the test name/comment ("the chip restores, the x deletes") and the owner's every-press-produces-a-visible-result rule are unguarded at this surface; the wave's user-facing contract is protected only at the API-arg level. Fix: after line 409, assert the "all-cheap" chip is gone from `presetsRow`; after 403, assert the restored status/routes (e.g., `getRoutes` was called again / status text). CONFIRMED.
- **[MEDIUM] Armed-face assertions cannot fail (finder predicate = asserted value)** - `line 400` and `line 406`. What: `chip(true)`/`del(true)` find buttons by `textContent === 'RESTORE "all-cheap"?'` / `=== "CONFIRM"`, then assert that same `textContent` `.toBe(...)` — the expectation is satisfied by construction; if arming breaks, the failure is an incidental `TypeError` on the `!` non-null crash, not the stated assertion. Trigger: any arming regression (e.g., `setArmed` dropped, or armed text reworded) — the expect lines give zero signal either way. Impact: class-1 defect — the recorded protection ("the armed flows assert the armed face text") is decorative; a reworded armed string "fails" only as a crash with a misleading stack. Fix: select the chip by stable means (position/aria) and assert its text transitions `all-cheap -> RESTORE "all-cheap"?`. CONFIRMED.
- **[MEDIUM] Mock lifecycle is order-coupled; cleanup lives in test bodies after the assertions** - `line 50` (beforeEach resets only `getKeys`/`setKey`) with `line 159` (hanging `testKey.mockImplementation`), restored only at `line 263`/`line 308`/`line 412-413`, all placed after assertions. What: `testKey`, `getRoutes`, `getCloudModels`, `routePreset` are never globally reset; the hanging `testKey` implementation from line 159 persists through tests 192-266; the counter-based `getRoutes`/`getCloudModels` implementations from tests 10-11 leak until each later test happens to override them. Trigger: one assertion throws in test 10/11/14 (e.g., line 247) — its tail restoration never runs; or a new key-row test is inserted anywhere after line 159's test and clicks TEST without reconfiguring `testKey` — it inherits the never-resolving probe and fails with a stuck "testing…" chip that reads as a production bug. Impact: class-4 — one real failure cascades and misdiagnoses; correctness of the file depends on the exact current ordering. Fix: an `afterEach` (the repo convention — `src/api/*.test.ts` all use one) doing `vi.resetAllMocks()` or resetting each shared mock, and seed defaults in `beforeEach`. CONFIRMED (latent today).
- **[LOW] Hand-tuned microtask flush counts with a near-zero margin at the DELETE arm** - `line 402` (three `await Promise.resolve()`) vs `line 405` (DELETE first press). What: the restore chain's `.finally(() => setPresetBusy(false))` (`SettingsConsole.tsx:240`) resolves roughly four microtask rounds deep; the next clicked button carries `disabled={presetBusy}` (`SettingsConsole.tsx:231`, `245`), and jsdom's `click()` returns early on disabled form controls — the arm would silently no-op and `del(true)` at 406 crashes as though arming were broken. It passes today only because act's exit flush absorbs the final round. Trigger: any one added `.then` link in the component's restore chain shifts the depth by one. Impact: class-6 fragility — a future benign component change breaks this test in a way that points at the wrong code.

## Bugs & vulnerabilities
- **[MEDIUM] The truncating GB display rule has a rounding twin in StatusFooter** - `tiers.ts:47-49` vs `src/components/StatusFooter.tsx:98` — CONFIRMED. What: tiers.ts:42-46 declares "one display rule everywhere a verdict speaks GB ... The displayed number never exceeds the truth" (gate 2026-09-02), but StatusFooter's `const gb = (n: number) => (Number.isFinite(n) ? (n / 2 ** 30).toFixed(1) : "—")` **rounds**. Trigger: any VRAM figure with a ≥ .95 tenth — e.g. the doctrine's own 8,587,870,208-byte card (7.9992 GiB) reads "7.9 GB" in the wizard (fmtGb, FirstRun.tsx:237) and "8.0" in the status footer; a 15.96 GiB card reads "15" vs "16.0". Impact: two surfaces disagree on the same server number at exactly the boundary the truncation rule was written for, violating the standing "GB figures must be truthful and match their source" invariant for whichever rule is deemed wrong. Fix is in StatusFooter (out of file, read-only review): route it through `fmtGb` (it already imports nothing from tiers — add the import) or replicate the floor. Not a defect in tiers.ts itself; named here as the twin per protocol.
- **[LOW] `catalogIds()` is dead code whose comment claims a validation it cannot perform** - `tiers.ts:157-161` — CONFIRMED (check_references: `is_referenced=false`, zero imports, zero content matches). What: the comment says "every id the ladder can name must exist in the catalogs" but the function returns the **full** catalogs' id lists (the superset), not the ladder's named ids — it structurally cannot detect a drift; and nothing calls it. The real enforcement is the vitest probe (tiers.test.ts "every id the ladder can name exists...") plus the downstream `if (manifest)` guard at vite.caliper.ts:403-406. Impact: dead export invites future misuse as a validator that validates nothing; the stale comment misleads the next editor. Fix: delete the function (and its comment), or make it return the ladder's own named ids so it matches its comment.
- **[LOW] Multi-CUDA machines are judged by the first device that reports VRAM, not by the device ComfyUI will use** - `tiers.ts:129-131` — PLAUSIBLE (code path traced; trigger requires unusual hardware). What: `find` takes the first `type === "cuda"` entry with `vramTotal > 0`. ComfyUI's `system_stats` preserves torch device order, and ComfyUI defaults to cuda:0, so first-is-correct in the common case. But if cuda:0 reports no `vram_total` (mapped to `undefined` at vite.caliper.ts:399) or a heterogeneous rig lists the smaller card first, the ladder silently judges cuda:1 — while the no-CUDA branch's reason (line 138, "no CUDA device answered the probe") is also reached when a cuda device DID answer but with an unusable `vram_total`, slightly overstating "never answered" against the truthfulness rule. Impact: verdict can understate the machine or name a card ComfyUI won't run on; the reason still names the judged card, so it stays checkable. Fix: prefer max-`vramTotal` among cuda devices, and split the no-CUDA reason from the "answered without numbers" case.
- **[LOW] Two non-null assertions whose safety is implicit cross-line coupling** - `tiers.ts:144-145` — CONFIRMED safe today, fragile tomorrow. `cuda.vramTotal!` holds only because the predicate three lines up checked `typeof === "number"`; `LADDER.find(...)!` holds only because the terminal rung's floor is `0` (line 116) and `vramGb > 0` is guaranteed by the same predicate. Neither invariant is enforced — `!` silences exactly the check TypeScript would perform, so editing the terminal floor above 0 (or reordering rungs) turns line 147 into `undefined.tier` — a crash at wizard load. Fix: `LADDER.find(...) ?? LADDER[LADDER.length - 1]` or an explicit invariant assert.

## Missing safeguards
- `fmtGb` (line 47) has no `Number.isFinite`/negative guard: `fmtGb(NaN)` → `"NaN"`, `fmtGb(-5)` → `"-5.0"`, `fmtGb(Infinity)` → `"Infinity"`. All current call sites are safe (judgeTier only passes `vramGb > 0`; JSON cannot carry Infinity), but the exported surface is unguarded while its StatusFooter twin guards with `Number.isFinite` — inconsistent robustness for the same quantity class.
- No runtime validation that LADDER ids resolve in the catalogs. The comment at lines 157-158 claims this contract, but it lives only in a test; the production guard at vite.caliper.ts:403-406 (`if (manifest) plans.push(...)`) **silently drops** a drifted id, so a catalog rename would ship a verdict whose tier text promises packages the wizard cannot install, with no error anywhere. Either validate LADDER ids against CATALOG/LLM_MODELS at module load (throw at startup, not at render) or log when `manifest` is not found.
- The terminal-rung invariant (see LOW above) deserves an explicit guard rather than a `!` — the failure mode is a first-run-wizard crash, the app's front door.

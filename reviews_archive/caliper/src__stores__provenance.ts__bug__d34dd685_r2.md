## Verdict

NOT shippable as-is — one HIGH confirmed: the store's write protocol (PUT the whole in-memory cache) can silently and permanently destroy server-side provenance records it has never seen, which is a second door to the exact catastrophe the 2026-08-28 separate-budget law was written to prevent. ## Bugs & vulnerabilities

**[HIGH] Stale-snapshot PUT replaces server-appended provenance records — silent permanent loss of REPRODUCE formulas** - `lines 36-42` (`persist`), with refresh sites `main.tsx:22`, `src/components/ScreenStage.tsx:732`, `src/surfaces/OutputsSurface.tsx:152`; server side `vite.caliper.ts:126-134` and `vite.film.ts:688+` — CONFIRMED (independently re-verified against current bytes by the hunt orchestrator: the PUT handler's whole-file atomicWrite, the film engine's ten appendProvenance call sites, and the queue-time saveProvenance at queueStore.ts:136 all read first-hand).
- What: every mutation (`saveProvenance` :81, `removeProvenance` :88, `patchProvenanceOutputs` :95) PUTs the entire in-memory `cache`, and the server PUT handler validates shape only, then `atomicWrite`s the payload over `provenance.json` — an unconditional whole-file replace with no merge, no version check, and no backup (backups exist only for workflow graphs, `backupExisting`). But `cache` is refreshed only at boot and on Library/Outputs mount; `queueStore.ts:136` calls `saveProvenance` at queue time on the Generate screen with no refresh, and the terminal patch fires wherever the app sits. Meanwhile records are appended SERVER-SIDE all session by a different writer on the SAME file: `appendProvenance` in vite.film.ts (film takes — "also used by the generic cloud-run path for standalone generations", per its own comment).
- Trigger (ordinary flows, no exotic timing): (a) boot → run an autopilot film (server appends up to 400 records) → queue a one-off on Generate → the queue-time PUT writes the boot-time cache over the file and wipes every film record appended since; (b) render via a cloud engine (server-side append) → next local queue clobbers the cloud record; (c) two windows (the store's own stated rationale, lines 20-21): window B's mutation PUTs its boot-time snapshot, resurrecting records window A deleted (the ghost family via a new door, not the fixed localStorage merge-back) and deleting A's adds.
- Impact: the library silently forgets those renders — prompts/seeds/params per artifact are unrecoverable (the rendered files survive on disk but the app's library is provenance-driven, so they become invisible in-app). This is precisely the "REPRODUCE formulas must never be lost" invariant; the 2026-08-28 fix closed eviction, not clobber. Borders CRITICAL under the rubric's data-loss clause; graded HIGH only because artifact files survive and single-window no-append sessions never trigger it.
- Fix: stop shipping snapshots. Either (1) record-level server ops (POST one record / DELETE by promptId / PATCH outputs by promptId) so the client never speaks for records it doesn't hold; or (2) optimistic concurrency — GET returns a version, PUT requires it (`If-Match`), server 409s on mismatch and the client refresh-then-retries; minimal stopgap: refresh-before-first-write-per-staleness (re-GET immediately before each PUT window), which shrinks but does not close the race.

- Trigger: corrupted or hand-edited `caliper.provenance` in this browser (the store itself no longer writes the key — it is a read-only legacy seed, so only pre-server-era data or outside interference can be wrong).

## Missing safeguards

- Fire-and-forget unordered writes: `void persist()` has no client-side serialization or versioning; two PUTs issued in quick succession (delete then save, or patch then delete) ride separate sockets and can land inverted on the server, leaving a deleted record standing server-side — the ghost family's PUT-ordering door. Same fix family as the HIGH above.
- The hydrate-vs-mutation window is unsynchronized (recorded 2026-08-26 for the patch flavor, self-healing). One ordering does NOT self-heal: a save landing inside an in-flight GET whose server read predates the PUT drops the record from the cache, and the later terminal `patchProvenanceOutputs` then no-ops — the record survives server-side but its outputs are never written (the terminal patch is the only outputs writer). Requires millisecond-scale surface-switch timing on localhost, so noted, not filed.
- `doHydrate` validates array-ness only, not record shape — a hand-edited or corrupted server file leaks malformed records into every consumer (the PUT route enforces promptId/bundle strings; the GET path trusts the disk).
- `provenance.json` is atomically replaced with no backup and no version stamp on records — both compound the HIGH finding's permanence (graph seeds get backups; the library's memory does not).

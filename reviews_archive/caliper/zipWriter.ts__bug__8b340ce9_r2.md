## Bugs & vulnerabilities

**[LOW] >65,535 entries overflows the EOCD count fields as a raw Node RangeError, not the file's loud refusal** - `line 89` (with `line 10` and `line 66`)
- What: the guard at `lines 45-48` polices only the 4 GiB byte ceiling. The EOCD entry-count fields at `lines 89-90` are `writeUInt16LE(entries.length, ...)`, which throws Node's documented RangeError above 0xffff — before that, the per-entry name length at `line 66` has the same unguarded UInt16 shape. The file's own comment (`lines 40-42`) states the doctrine: zip32 limits "refuse loudly instead, the caller says 'export in smaller parts'".
- Trigger: an export whose selection exceeds 65,535 entries (65,536th file, counting the manifest entry the consumer appends at `vite.library.ts:159-167`) while the 4 GiB guard stays quiet — possible only when average entry size is under ~64 KiB (65,536 x ~64 KiB ~ 4 GiB), e.g. a mass export of small preview/metadata artifacts. The repo's own fixture PNG is 96 bytes, so small entries are a sanctioned shape.
- Impact: no corruption (the throw precedes any write), but the user's error sentence becomes Node internals ("The value of \"value\" is out of range...") forwarded by the consumer's catch (`vite.library.ts:208-210`) as the 500 body — a truthfulness-adjacent failure of the file's own honesty pattern, and an untested boundary.
- Fix: extend the guard — `if (entries.length > 0xffff) throw new Error(`the export is ${entries.length} files - zip32 counts at most 65,535; export in smaller parts`)`, and optionally reject `nameBuf.length > 0xffff` alongside it; add the third refusal shape to `zipWriter.test.ts`'s refusal block (`lines 50-59`), which already parameterizes both 4 GiB shapes.
- Phase 3: CONFIRMED — traced `buildZip` line 89 -> Node `writeUInt16LE` RangeError (documented behavior) -> guard at 45-48 cannot preempt when entries are small -> handler catch at `vite.library.ts:208` forwards `e.message` verbatim. Runtime reproduction unnecessary for a documented throw; the 65k-small-files trigger is the PLAUSIBLE part (not reachable with today's typical multi-MB media, hence LOW).

## Missing safeguards
- `buildZip` accepts duplicate entry names without complaint (spec-permitted; extractors overwrite or balk). The consumer's collision rename (`vite.library.ts:138-139`) checks only the pre-rename name against its `seen` set, so a third collider of the same length lands on an already-used renamed name. Traced and currently harmless — same type+subfolder+filename implies the same absolute path, so any duplicate is byte-identical — but a one-line `if (seen.has(renamed))` recheck or a duplicate-name assertion here would close the shape permanently.
- Entry-name hygiene (`..` components, drive letters, backslashes) is trusted entirely to the caller per the interface doc (`lines 26-27`); the sole non-test caller does sanitize (`vite.library.ts:33-35` filters `.`/`..`, `line 25` SAFE_NAME blocks path separators in filenames). A future caller can reintroduce zip-slip-shaped archives unnoticed — a cheap `name.split("/").includes("..")` refusal would make the writer self-defending.
- `dosDateTime` (`lines 33-37`) wraps silently outside the DOS epoch: a pre-1980 date reads back as the 2100s, past 2107 truncates. Dormant — no current caller passes `at` (`vite.library.ts:54` equivalent always uses `new Date()`).
- Name byte-length > 65,535 (`line 66`, `line 81`) is the same unguarded UInt16 class as the finding above; unreachable through the current consumer (filesystem-bounded names) — fold into the same guard if added.
- Cross-file, out of unit (route to vite.library.ts's own dispatch): type "temp" artifacts are accepted by `resolveArtifact` (`vite.library.ts:31`, root map `lines 20-23`) but filed under `output/<subfolder>/...` in both the archive paths and the manifest (`vite.library.ts:137`) — the entry's claimed home is not its real one, a consumer-side truthfulness defect, not a `buildZip` contract break.

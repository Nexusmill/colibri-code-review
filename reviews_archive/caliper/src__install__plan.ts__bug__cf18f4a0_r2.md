## Bugs & vulnerabilities

**[LOW] `partial-manual` collapses "nothing present, all manual" into a label that promises partial presence** — `line 35` (comment at lines 20-22)
What: The comment defines the state as "everything fetchable is here, what remains needs a human", but the code only tests `downloadable.length === 0`. Two distinct situations map to the same state: (a) some files present, only manual gaps remain (the documented case), and (b) ZERO files present and every missing file is manual — an all-manual, fully-absent bundle. In case (b) `files.every(f => !f.present)` is true, yet the plan declares itself "partial".
Trigger: A `BundleManifest` whose files all lack `url` (e.g. all Civitai-login-gated), called with an empty/all-false `present` record — plan returns `state: "partial-manual"` with `manual` = every file.
Impact: None today — verified that no consumer matches the string "partial-manual" (BundlesSurface.tsx lines 301/442 branch on `state === "installed"` and `downloadable.length`; the recommend wizard's plans flow through the same badge components), so the badge honestly renders "N manual files". The defect is the exported contract: any future consumer branching on `state === "partial-manual"` to mean "mostly installed" (e.g. a wizard progress step) will be lied to, and the comment already misstates the invariant. Under this repo's truthfulness bar that is a latent MEDIUM held to LOW only by the absence of a consumer.
Fix: Either make the ternary match the comment — `missing.length === 0 ? "installed" : downloadable.length === 0 ? (files.some(f => f.present) ? "partial-manual" : "manual-only") : "missing"` — or, minimally, rewrite the comment to the condition the code implements: "partial-manual = nothing left to click; whatever is missing needs a human (whether or not anything is installed yet)". Add the case-(b) shape to plan.test.ts either way.
Confidence: CONFIRMED (direct read of line 35; comment lines 20-22; repo-wide search shows the string consumed nowhere in src/ outside plan.ts and plan.test.ts).

## Missing safeguards
- `present` keys are trusted verbatim: `present[f.name] === true` (line 26/30) silently treats an absent key as "file missing". The sole producer (`scanPresent`, vite.caliper.ts:386-395) keys by the identical `f.name`, so the shipped wiring cannot skew — but nothing in plan.ts or its type would surface a caller that passes paths, lowercased names, or a partial map. A dev-only assertion (every manifest name has a key) would pin the contract cheaply.
- `FileState.downloadable: !!f.url` (line 27) reports fetchability, not actionability — it is `true` for files already on disk. `files[]` is currently unrendered per-file, so nothing misleads yet, but a future per-file "download" affordance built on this field would offer to re-fetch present files. A name like `hasSource` (or `downloadable: !present && !!f.url`) would prevent that trap.
- Duplicate filenames within one manifest would collide in any `Record<string, boolean>` `present` map (last `fs.access` wins in scanPresent). plan.ts itself is faithful to degenerate input and the guard belongs to catalog validation (adjacent, pinned file) — noting only that no uniqueness test covers CATALOG file names per manifest, unlike the LLM_MODELS id-uniqueness test at plan.test.ts:58-69.

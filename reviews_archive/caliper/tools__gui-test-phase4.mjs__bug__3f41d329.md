## Verdict
Surprisingly intact for an old-generation tool: every selector it touches still exists verbatim in the current UI — "OPTIMIZE"/"SET UP AI"/"AI ON" as the deck button label (src/components/DeckControls.tsx:63-75), the "CONSOLE" taskbar key rendered when `llm?.running` (src/components/ScreenStage.tsx:77-79), `input[aria-label="Ask the optimizer"]` (ScreenStage.tsx:273), `button[aria-label="Close console"]` (ScreenStage.tsx:221), `.agent-body`/`.agent-console` (ScreenStage.tsx:223, src/styles/chassis.css:1583/1607), and the T2 grounding markers "WDDM"/"vram-headroom" still live in knowledge/comfyui-optimization.md with citations rendered as `source :: heading` (ScreenStage.tsx:235), so the `::` check holds. The defects are hygiene, not drift: it cannot fail, it leaks the VRAM-bearing sidecar if it crashes mid-flow, and its screenshots directory is untracked noise. Deletion is safe — nothing references it.

## Bugs & vulnerabilities
- **[MEDIUM] Test cannot fail — every check is a console.log and the process always exits 0** - `lines 29-88` — CONFIRMED. What: T1-T4 outcomes ("AI ON reached", "reply grounded", "console closed", "sidecar stopped") are only logged; there is no `process.exit(1)` anywhere and no thrown assertion. Trigger: any regression — button renamed, console never opens, reply ungrounded. Impact: the tool runs green in any automation that checks exit codes (the way `npm run test:ui` and sibling see-ui-720p.mjs:53 do with `process.exit(2)`), so UI breakage ships silently; as a manual tool it still relies on the human reading eight log lines. Fix: track a failure flag and `process.exit(1)` at the end when any check is false (or fold the still-relevant flow into tools/ui-harness.mjs, the current-generation harness, and delete this one).
- **[MEDIUM] No try/finally — a crash between AI-on and AI-off leaks the llama sidecar (VRAM held on the shared 16 GB card) plus an orphan page** - `lines 20-91` — CONFIRMED (structure; trigger plausible). What: T1 starts the optimizer (`llmStart` — the local path purges ComfyUI's resident models first) and only T4 (lines 83-89) stops it; `page.close()`/`browser.disconnect()` at lines 90-91 are only reached on the happy path. Trigger: any throw after the sidecar is up — `optimize.click()` or `input.type()` on a detached handle, an Edge/CDP hiccup, a navigated-away page. Impact: the sidecar keeps holding GGUF VRAM with ComfyUI's models already purged, on a card this repo treats as a shared, cost-bearing resource; the driven Edge also accumulates an orphan tab (it survives between runs by design). Fix: wrap the post-connect flow in try/finally that (a) clicks "AI ON"/calls stop if the AI was started, (b) `page.close()` + `browser.disconnect()`.
- **[LOW] Stale fallback semantics: the "SET UP AI" path now kicks a ~3 GB provision download, so the 90 s "AI ON" wait can never succeed there** - `lines 28-39` — CONFIRMED. What: the header comment "max 90s: purge + model load" describes the old local-only world; DeckControls.tsx:45-53 now routes a "SET UP AI" click to `llmProvision()` (a ~3 GB llama.cpp + model download) and `llmStart` to the cloud brain by default ("no VRAM touched", DeckControls.tsx:46). Trigger: running the tool on a machine where the local brain isn't provisioned and no cloud key exists. Impact: the test downloads gigabytes it didn't used to (the repo's one sanctioned outbound is consented model downloads — this is the app's own flow, but the operator consented to a GUI test, not a 3 GB fetch) and then correctly-but-misleadingly logs `AI ON reached: false` while the label reads "↓ X MB". Fix: drop the "SET UP AI" fallback (treat it as skip-with-failure), refresh the comment.
- **[LOW] T2 grounding check is a race against ellipses — a good reply containing "…" spins the full 180 s and reports a false negative** - `lines 58-67` — PLAUSIBLE. What: the loop only breaks when `/WDDM|vram-headroom/i` matches AND the reply contains no "…" (U+2026); busy placeholders ("waking the optimizer…", "still thinking…", ScreenStage.tsx:263) all contain U+2026, which is what the guard is for — but a *final* grounded answer that quotes an ellipsis or doesn't literally contain WDDM/vram-headroom (both markers do exist in today's knowledge corpus — verified) keeps polling 60×3 s and logs `reply grounded: false`. Impact: wasted 3 minutes and a misleading log; no wrong action. Fix: break on `busy` state clearing (SEND button re-enabled / pulse span absent) instead of string heuristics.
- **[LOW] Screenshot evidence directory is not gitignored, unlike its siblings** - `line 7` — CONFIRMED. What: `gui-test-screenshots/` is created in CWD; .gitignore covers `see-shot*.png` (line 16) but not this directory. Impact: every run dirties `git status` with a dozen `t*.png` files; an agent in a hurry may commit them. Fix: add `gui-test-screenshots/` to .gitignore, or delete the tool.

## Missing safeguards

- ElementHandles from `page.$$("button")` are never `.dispose()`d — bounded leak within a short run, noted for completeness.
- No documentation trail: nothing in docs/HISTORY.md, docs/FEATURES.md, or package.json references this tool — it is dead weight from phase 4; deleting it breaks nothing (rebaseline.mjs's header references only ltx-720p-test.mjs).

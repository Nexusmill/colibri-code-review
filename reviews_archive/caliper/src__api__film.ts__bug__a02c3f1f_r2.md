## Verdict
Not clean — the POST surface is solid (every wrapper rides the shared `post()` with a real error contract), but all three GET wrappers bypass that contract, and one of them feeds a consumer that silently erases the wizard's live run view on any server error. Small fixes, real defects; nothing here burns money directly, but two of the three violate the truthful-status doctrine by rendering server failures as benign empty state.

## Bugs & vulnerabilities

- **[HIGH] `autopilotStatus` blind-casts error bodies — a 404 erases the wizard's live producing record — `line 191`**
  What: `fetch(...).then((r) => r.json())` with no `res.ok` check and no error-body detection. The server's GET handler answers a failed run read with `send(404, { error: "no such run" })` (vite.film.ts, GET `?autopilot=1&id=` catch branch), so on any read failure the client returns `{ record: undefined, job: undefined }` cast as the full status shape — the promise resolves, never rejects.
  Trigger (two live paths): (1) the run is deleted from the RUNS window while the wizard polls it at a checkpoint/halted phase — delete is only refused while `produceRunning()` is true, and phase `"checkpoint"` is explicitly not running; the background recycle removes the dir and the next 3-second poll gets the 404. (2) The `autopilot.json` read/write race: `writeAutopilot` (vite.film.ts:67-70) uses plain truncate-then-write `fs.writeFile` — non-atomic — while the pipeline writes checkpoints/spend throughout a run and FilmWizard polls every 3000 ms; a poll landing inside the write window makes `readAutopilot`'s `JSON.parse` throw → 404 → same wipe, purely transient.
  Impact (consumer cited): FilmWizard.tsx:768-769 adopts it unconditionally — `setDraft((d) => d.record ? { ...d, record: r.record } : d)` replaces the truthy live record with `undefined`, and the `.catch(() => {})` never fires because the promise resolved. The poll effect's deps `[record?.step, record?.id]` go undefined → interval torn down → the producing view (progress, checkpoint verdict cards) silently vanishes and never recovers, even when the very next poll would have succeeded. The owner loses the APPROVE/REJECT surface mid-run — the run stalls at an invisible checkpoint. The wizard's own open-run path guards this (`if (!r.record) throw new Error("no such run")`, FilmWizard.tsx:944-945); only the producing poll is exposed. CONFIRMED (both sites read; trigger traced end to end; independently re-verified against current bytes by the hunt orchestrator).
  Fix: in `autopilotStatus`, check `r.ok` and the error body and `throw` (the file's own `filmBatteryStatus`, line 296, already does exactly this) — the wizard's existing `.catch(() => {})` then becomes the intended resilience: keep the last record, keep polling.

- **[MEDIUM] `autopilotList` writes `undefined` runs into a `| null` store on any server error — `line 111`**
  What: `(await (await fetch("/api/film?autopilot=1")).json())` — no ok-check, no json-catch. Any error the middleware's outer catch answers as JSON (`{ error: ... }`) parses fine and is returned with `runs` absent; a non-JSON error body rejects as a raw SyntaxError instead of a readable error.
  Trigger: any throw inside the list branch (fs error reading `films/`, corrupt state file), or a proxy hiccup returning a non-JSON body.
  Impact (consumer cited): filmRunsStore.ts:94 `set({ runs: r.runs, ... })` stores `undefined` into `runs: AutopilotRunSummary[] | null` — `null` is the consumers' "loading" sentinel, `undefined` falls through null-guards; `derivePin` then throws on `runs.find(...)` inside the same try, so the catch sets `listError` but never resets `runs` off `undefined`. The RUNS window's null-skeleton path does not match undefined. Store corruption CONFIRMED by code read at both sites; the exact render symptom in FilmRuns.tsx is unverified because the row-render guard was not read in full.
  Fix: parse with the same guard pattern — `if (!res.ok || data.error) throw`, and default `runs` to `[]` only on a 2xx body that actually has it.

- **[MEDIUM] `filmList` renders every server error as an empty library — `line 71-75`**
  What: `res.json().catch(() => ({}))` then `data.films ?? []`. A 500 answered with `{ error }` parses successfully → `films: []`; a non-JSON error body hits the catch → `{}` → `[]`. The function never rejects on HTTP errors, so the only failure the consumer can show never reaches it.
  Trigger: any throw in `listFilms()` (one corrupt `film.json` under `films/` is enough — these files are written with the same non-atomic pattern) or any non-2xx/non-JSON response from the route.
  Impact (consumer cited): OutputsSurface.tsx:154 sets `filmError` only in `.catch` — this path resolves, so the FILM ASSETS division renders empty with no error line. Under the truthful-status doctrine a backend failure reads as "your films are gone." CONFIRMED mechanism by code read at both sites; the exact server-side throw is PLAUSIBLE (unverified because `listFilms` internals were not read in full).
  Fix: same as above — check `res.ok`/`data.error` and throw; the OutputsSurface error strip already does the right thing on rejection.

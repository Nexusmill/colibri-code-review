## Bugs & vulnerabilities
- **[LOW] eachlabs account extractor reads a wrapped `{models}` shape the endpoint never answers — the enrichment is dead code, and a naive shape fix would make the chip lie** — `line 44` (counter-site: `src/providers/eachlabs.ts:68`-77).
  **What:** the probe's account reader is `countLabel((b as { models?: unknown })?.models)`, but the eachlabs `/v1/models` endpoint answers a **bare array** — the repo's own adapter (`listEachLabsModels`) grounds the bare-array shape live (2026-08-22) and its BUGHUNT11 guard (fixed 2026-09-16, after the prior review's bytes) explicitly refuses `{models: []}` as "eachlabs models: the response was not a model list". A bare array has no `.models` property, so `account` is always `undefined` and the EachLabs row can never say more than "live". The grounding comment at line 12 ("the adapter's own listEachLabsModels call") cites an adapter whose contract the extractor contradicts — comment staleness and code break in one.
  **Trigger:** every successful eachlabs probe.
  **Impact:** contained — the verdict itself stays truthful; the documented enrichment ("a short account label from the 200 body, when the service offers one") never fires for one of six services. The landmine: fixing the shape alone (`countLabel(b)`) makes the chip say "live · 1 models" forever, because the probe's own `?limit=1` page size would be read as the account's model count — an untruthful display for the "500+ models" account the serviceKeys hint itself advertises.
  **Fix:** read the bare array AND keep the count honest — either drop the eachlabs count (`account: () => undefined`) or mirror the adapter's `?limit=500` so the array length is the real catalog size; correct the line-12 comment either way. Verified against the adapter's test (`src/providers/eachlabs.test.ts:114`-125, wrapped-payload refusal) — live-service probing was not available in this environment, but the repo's recorded ground truth is unambiguous.
